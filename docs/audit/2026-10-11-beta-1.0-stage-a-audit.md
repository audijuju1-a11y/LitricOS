   `.git` first. This is recorded as a project-level risk, not an
   inconvenience.
3. `ci/verify.sh` is the only gate that exists; there is no CI workflow that
   runs it automatically.

> **Recommendation for the user, not a blocker for Stage A:** restore the

> reviewed and reverted independently as the roadmap requires.

### 3.1 Contradictions found between docs and the tree (recorded, not silently resolved)

1. **[ARCH-00-boundaries.md](../ARCH-00-boundaries.md) §5 and
   [REPO-00-layout.md](../REPO-00-layout.md) §1/§2 still describe a

2. `REPO-00-layout.md` describes `shell/tokens/`, `defender/onaccess/`, `ai/`,

   system workspace" as a blanket rule, while the workspace comment in
   `src/Cargo.toml` names `litric-shell` and `litric-defender` as **platform**
   crates that are expected to take dependencies later. The two are consistent
   only if the platform-crate exception is treated as already granted.

## 5. Backend reality: what the OS can actually be asked to change

This is the single most consequential Stage A finding for the prompt set's
Waves 3–5 (network, Bluetooth, boot/login/lock).

| Backend the prompt set assumes | Present in this tree? | Evidence |
|---|---|---|
| `NetworkManager` (D-Bus or libnm) | **No** | `grep -ri` for `zbus\|libdbus\|networkmanager\|bluez\|pipewire\|upower\|polkit\|pam` across `src/` matched **one example file** and `image/mkosi.profiles/desktop.conf`; no crate depends on a D-Bus binding and no `[[bin]]` talks to a service |
| `BlueZ` | **No** | same |
| `PipeWire` / WirePlumber | **No** | same |
| `UPower` | **No** | same |
| `polkit` authorization | **No** | same |
| **PAM / authentication of any kind** | **No** | `SYSTEM-SCOPE.md` Part B6 rows 226–239 (`S`/`T`) and the 2026-08-29 note: *"There is no lock screen, because there is no authentication subsystem and a lock that accepts anything is worse than none."* |
| systemd as PID 1 | Yes (units in `image/mkosi.extra/usr/lib/systemd/system/`) | `CONFIRMED_IN_SOURCE` |
| The project's own IPC: `litric-sysd` over `/run/litric/sysd.sock` | Yes | ADR-0016, `litric-sysd` bin |

**Implication:** the prompt set's chain "Settings → typed provider → existing
Linux service" has **no existing provider to extend** for network, Bluetooth,
audio, power or authentication. Those waves are not refactors; they are new
privileged-system integration plus a new authorization boundary, and the prompt
set itself says such work must be preceded by a design note and threat model
rather than dispatched as a code ticket. They are marked `BLOCKED (no
prerequisite architecture)` in the gate matrix.

## 9. Risk map for the Beta 1.0 attempt

| # | Risk | Class | Why it matters |
|---|---|---|---|
| A-R1 | No version control in the checkout | process / data-loss | Patches cannot be reviewed, bisected or reverted; "preserve user changes" is unenforceable |
| A-R2 | Network/Bluetooth/audio/power/auth have no backend and no privileged-service design | security-critical | Wave 3–5 work would invent a trust boundary; the prompt set forbids doing that speculatively |

| A-R7 | No CI workflow; `ci/verify.sh` runs only when a human runs it | process | Gates can go stale silently, which `EVIDENCE.md` already demonstrates |
