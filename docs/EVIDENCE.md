### The clippy finding this run produced

The 2026-10-11 record's `PASS cargo clippy` was produced on `MINGW64_NT` (see the
header of this file). On Windows every `#[cfg(unix)]` and
`#[cfg(all(test, unix))]` module is **not compiled**, so `--all-targets` never
linted them. Run on Linux, the same command reported 12 findings in code that the
Windows run could not see, including two that mattered: a `panic!`/`expect` pair
in a helper that only exists on Unix, and integer arithmetic in a path decoder.
All 12 are fixed and the command now exits 0 on the Linux builder. The lesson is
recorded rather than the fixes alone: a lint result is only as wide as the
cfg-gates of the host it ran on, and this gate has to be run on Linux to mean
anything.

#### The partial-redraw oracle failed, and the renderer was not at fault

`cargo test -p litric-shell --bin litric-shell a_partial_redraw_is_pixel_identical`
failed on the first step with `18768` pixels differing from a full redraw within
`(29,59)-(388,358)`, worst channel difference `42`, while the frame's damage was
two 20x26 rects. Instrumenting the oracle to redraw twice from the same state
separated the two hypotheses in one run:

```
full-vs-full=0   partial-vs-full=18768
```

A full redraw is idempotent, so the renderer was not producing different pixels
from the same state — a frame had been composed whose damage did not cover
everything that had changed. That is [BUG-0019](bugs/BUG-0019-a-snap-that-changed-the-value-reported-no-frame.md):
`Anim::step` returned `false` on a settle-budget snap that moved the value, and
`Shell::tick` reads `false` as "nothing to draw". Fixed; after the fix every step
of every journey reports `partial-vs-full = 0`.

### The frame-budget warning now exists

`docs/PERF-budget.md` §4 claims the shell "logs a warning on every over-budget
frame". It did not: no code compared a frame's duration to the life state's
interval. The display loop now measures composition-to-presentation per frame
against `Shell::frame_interval_ms()` and logs the first ten over-budget frames and
every hundredth thereafter (rate-limited so a persistently over-budget desktop
does not make the journal the largest cost in the loop), and writes
`frames_drawn=` and `frames_over_budget=` into the status file. The rate-limit
policy is a pure function with its own test
(`main::tests::over_budget_logging_is_rate_limited_but_never_silent`). No
end-to-end run of this path exists here — `run_display` needs a framebuffer, and
this container has none — so the counter's runtime behaviour is **NOT RUN**.

### A locked frame costs 35.8 ms, and a QEMU window shows the surface — 2026-10-15

Two things were established on a second host (Windows 11,
`stable-x86_64-pc-windows-gnu`, the same release profile), neither of which the
WSL2 measurements above could show.

**BUG-0018 is fixed.** The frame that opens a locked session fell from 293.727 ms
to **35.819 ms** (8.2x), and from 10 426 249 pixels to **1 909 744**; the entry
sheet 311.362 → 37.983 ms, motion "Still" 306.114 → 36.843 ms, and the customize
sheet 477.656 → 185.718 ms (2.6x — still 5.6x over its own interval). Most of the
win is not the blur this record named as the prime suspect: **5.62M of the 10.43M
pixels were text layout**, because the clock and the entry sheet re-shaped the same
strings on every frame. The rest is a cached blurred backdrop (with touching
regions merged before blurring, because two overlapping blurs re-blurred in place
do not equal one blur of their union) and a locked frame no longer copying the
wallpaper underneath the opaque lock background — a skip proven invisible by
`frame_dump`: the fingerprints of 11-lock, 12-lock-password and 13-lock-customize
are byte-identical with and without it (0x367c7dc0b89dca35, 0x3ba8b424d52ac4f9,
0xb57ffe3c0e3e5b5d). Raw lines:
`docs/evidence/2026-10-15/bug0018-bench-final.log`. `cargo test --workspace` on
that host: 1095 passed, 0 failed.

**A display has now shown this surface.** `tools/run-qemu.ps1 -Gui` opens the real
QEMU window (SDL) with a USB tablet and a USB keyboard, booting UEFI from the split
edk2 firmware QEMU ships rather than from a download. Verified by the monitor, not

over black. Picture: `docs/evidence/2026-10-15/qemu-gui-smoke.png`.

What this does **not** establish: the guest was an empty raw image, because this
checkout has no bootable Litric image (`tools/build-image.sh` needs a Linux host
with `mkosi`, and this host has no WSL). So a person has driven *a* QEMU window with
their own pointer and keyboard; nobody has yet driven *Litric* in one, and the
1.75 FPS lock screen of the record above has never been seen on a screen.
