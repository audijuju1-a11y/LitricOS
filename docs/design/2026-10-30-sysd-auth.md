# Account creation and password change live in `litric-sysd`

Status: implemented for §72.

## Decision

The shell never spawns a credential helper and never holds a password in an
argument vector or an environment block. `litric-sysd` owns the privileged path,
because it is already the one process that runs `unix_chkpwd` for verification
(`providers.rs`), and because a daemon that may run `useradd` and `chpasswd` must
not be reachable through the compositor's input path.

This follows the rule recorded in `src/litric-sysd/src/providers.rs`: there is no
password database, no hash format and no PAM FFI in this tree. Passwords travel on
standard input to the distribution's own helpers, exactly as `unix_chkpwd` already
receives them. `chpasswd` reads `name:password` from stdin; `useradd` receives no
secret at all.

## Validation

One function, `litric_sysd::auth::validate_password`, is the single rule set:
account names match `[a-z_][a-z0-9_-]{0,31}`, passwords are at least 12 characters,
confirmation must match, and a password may not equal the account name. The shell
may call the same function before sending a request; the daemon validates again
and does not trust the socket.

## Wire syntax and capability

Three verbs, all authorised by the existing `AuthSession` capability scoped to
`lock://<user>`; no new capability id was added, because the vocabulary already
carries the live-consent one and the grant table already covers `lock://`.

```
AUTH VERIFY <user> <password-hex> [CONFIRM]                  (unchanged)
AUTH CREATE <user> <password-hex> [CONFIRM]                 (short form)
AUTH CREATE <user> <password-hex> <confirm-hex> [CONFIRM]   (long form)
AUTH CHANGE <user> <current-hex> <new-hex> [CONFIRM]        (short form)
AUTH CHANGE <user> <current-hex> <new-hex> <confirm-hex> [CONFIRM]
```

Both spellings are accepted by one parser. The short form takes the confirmation
to be the password (or the new password) itself, so it passes the same validator
without inventing a second value. The long form carries the confirmation as its
own field so a mismatch is refused before a helper is spawned. The two are
unambiguous: a field at the confirmation position that is the literal `CONFIRM`
is the consent word, and `CONFIRM` is not valid hexadecimal, so it can never be
mistaken for a hash. A caller that sends a non-hex value in a password position
gets `<not hex>` back, never the value.

Every password field is hex. `CONFIRM` is the live-consent word: without it the
broker refuses the action before the backend is reached, which is why the shell
sends it on all three.

## No request encoder, on purpose

Clients compose the line themselves (the shell's lock path already formats
`AUTH VERIFY ...`); the daemon only parses. There is no `Request::to_line()` and
this batch does not add one, because it would have to cover every verb and
duplicate formatting that already lives at each caller, with no runtime caller
of its own. The stability guarantee is instead tested at the parser boundary:
`compose` (test-local, canonical) → `parse` → `compose` must be byte-identical,
and parsing the recomposed line must yield the same action. The legacy
`AUTH VERIFY alice 77726f6e67 CONFIRM` line is asserted byte-for-byte.

## Scrubbing is best effort, and that is recorded

`litric_sysd::auth::scrub` overwrites the bytes, clears the vector and releases
its capacity. The crate has `#![forbid(unsafe_code)]`, so this cannot promise the
compiler or allocator never copied the bytes elsewhere. A hard guarantee needs the
`zeroize` crate (a new dependency) or a scoped `unsafe` `write_volatile` (which
would require relaxing the crate lint). Neither is taken silently; the limitation
is reported with the batch rather than hidden behind the word "zeroized".

## The provider runs the helpers through the daemon's runner

`SystemAuthProvider` implements `AuthProvider` on top of `action::Runner`, the
same process seam the rest of the daemon uses. Create runs `useradd` and then
`chpasswd`; change runs `unix_chkpwd` and only then `chpasswd`. A non-zero first
step returns without starting the second, a wrong current password maps to
`VerifyFailed`, a spawn failure to `SpawnFailed`, and standard input is scrubbed
after each step. Tests use a recording runner, so no root and no `/etc` write is
needed.

## Dispatch

`Sysd::action` checks the capability and consent exactly as before. A
verification keeps the single-plan path (`providers::auth_plan` →
`unix_chkpwd`), byte for byte. Create and change go to `Sysd::account`, which
calls `auth::validate_password` and then the injected `AuthProvider`
(`SystemAuthProvider` in production, `FakeAuth` in tests). A refusal carries the
`AuthError` token and a fixed sentence; the reply never repeats a field.

## What the tests can and cannot prove

The machine that runs CI has no root. Tests therefore prove command construction
(`argv` carries no password, stdin has the exact shape), the validation table, the
scrub helper, and the full create → change → verify flow against `FakeAuth`, an
in-memory `AuthProvider`. They do **not** run `useradd`, `chpasswd` or
`unix_chkpwd`; that path needs a privileged integration run and is not claimed.
The state test drives both spellings of `AUTH CREATE` and `AUTH CHANGE`
through `Request::parse` and `Sysd::handle` against `FakeAuth`, so validation,
capability, consent and dispatch are covered together. The parser-boundary test
proves recomposition stability and that `AUTH VERIFY` keeps its exact line.
