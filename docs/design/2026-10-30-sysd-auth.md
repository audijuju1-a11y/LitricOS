# Account creation and password change live in `litric-sysd`

Status: accepted for §72 (batch in progress).

## Decision

The shell never spawns a credential helper and never holds a password in an
argument vector or an environment block. `litric-sysd` owns the privileged path,
because it is already the one process that runs `unix_chkpwd` for verification
(`providers.rs`), and because a daemon that may run `useradd` and `chpasswd` must
not be reachable through the compositor's input path.

This follows the rule recorded in `src/litric-sysd/src/providers.rs`: there is no
password database, no hash format and no PAM FFI in this tree. Passwords travel on
standard input to the distribution's own helpers, exactly as `unix_chkpwd` already
receives them. `chpasswd` reads `name:password` from stdin; `useradd` receives no
secret at all.

## Validation

One function, `litric_sysd::auth::validate_password`, is the single rule set:
account names match `[a-z_][a-z0-9_-]{0,31}`, passwords are at least 12 characters,
confirmation must match, and a password may not equal the account name. The shell
may call the same function before sending a request; the daemon validates again
and does not trust the socket.

## Scrubbing is best effort, and that is recorded

`litric_sysd::auth::scrub` overwrites the bytes, clears the vector and releases
its capacity. The crate has `#![forbid(unsafe_code)]`, so this cannot promise the
compiler or allocator never copied the bytes elsewhere. A hard guarantee needs the
`zeroize` crate (a new dependency) or a scoped `unsafe` `write_volatile` (which
would require relaxing the crate lint). Neither is taken silently; the limitation
is reported with the batch rather than hidden behind the word "zeroized".

## The provider runs the helpers through the daemon's runner

`SystemAuthProvider` implements `AuthProvider` on top of `action::Runner`, the
same process seam the rest of the daemon uses. Create runs `useradd` and then
`chpasswd`; change runs `unix_chkpwd` and only then `chpasswd`. A non-zero first
step returns without starting the second, a wrong current password maps to
`VerifyFailed`, a spawn failure to `SpawnFailed`, and standard input is scrubbed
after each step. Tests use a recording runner, so no root and no `/etc` write is
needed.

## What the tests can and cannot prove

The machine that runs CI has no root. Tests therefore prove command construction
(`argv` carries no password, stdin has the exact shape), the validation table, the
scrub helper, and the full create → change → verify flow against `FakeAuth`, an
in-memory `AuthProvider`. They do **not** run `useradd`, `chpasswd` or
`unix_chkpwd`; that path needs a privileged integration run and is not claimed.
